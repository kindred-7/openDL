# 签名发布与应用更新

## Windows 安装器构建与覆盖安装

Windows 发布包使用项目维护的安装器，发布者在 Windows 上手动运行：

```powershell
./scripts/build-windows-installer.ps1 -Architecture amd64
```

脚本调用 MyGo 构建，并用 NSIS 重新生成 `build/windows-amd64/OpenDL.Setup.<版本>.amd64.exe`；也可指定 `-Architecture arm64` 和 `-Makensis <路径>`。不要发布直接运行 `go tool mygo build` 生成的默认安装器：它没有覆盖安装前的退出处理。自定义安装器生成失败时脚本会删除默认安装器，防止误发布。若需要 Authenticode，须在生成后对最终安装器单独签名，再计算发布清单的大小和摘要。

`mygo.json` 中的 `version` 会由 MyGo 写入程序版本，同时用于安装包文件名和安装登记。配置正式更新源时，MyGo 通过 `MYGO_LDFLAGS` 接收额外链接参数；例如在发布环境设置：

```powershell
$env:MYGO_LDFLAGS = '-X main.officialUpdateURL=https://updates.example.com/opendl/releases.json -X main.officialUpdatePublicKey=替换为Base64公钥'
./scripts/build-windows-installer.ps1 -Architecture amd64
```

示例地址和公钥需要替换；不要把私钥放入链接参数。构建完成后，发布者应确认已安装程序显示的版本与安装包、签名清单一致，并确认正式更新源已生效。

安装器覆盖前会提示用户，向目标路径的新版应用发送带本机令牌的退出请求，应用暂停下载、等待任务停止并冻结新任务后退出；安装器等待可执行文件解除占用。旧版本没有该请求接口，安装器尝试关闭其主窗口；交互式安装在用户接受最初的提示后，若等待超时仍检测到目标路径的进程，会自动强制结束该进程，可能导致下载中断或未保存状态丢失。静默安装不会强制结束进程。若其他程序占用文件或路径不可写，安装器提示排查后重试。覆盖前会备份旧版可执行文件；写入失败时尝试恢复，恢复失败时保留临时备份并提示位置。此恢复仅覆盖程序文件，不保证回滚已写入的扩展资源；安装前仍应保留可靠的发布包和备份。

现有发布安装包不会因源码变更而获得上述行为，必须由发布者构建并发布新的安装包。手动验证应覆盖：新版及旧版运行中升级、后台驻留、活动下载、多个实例、文件被其他程序占用、无写入权限、静默安装和取消安装。

新安装器默认读取当前用户上次登记的安装位置，也可在安装界面或通过 `/D` 指定目录；完成页可选择创建桌面快捷方式。其卸载器也会先尝试让应用退出，程序文件无法删除时保留卸载入口供重试；卸载不删除用户的配置、下载记录和下载文件。

官方更新源配置为 GitCode 仓库 `kindred-wu/openDL` 最新正式发行版中的 `releases.json`，应用内置原有 Ed25519 公钥。首次启用该方案前，必须发布包含签名清单及安装包的正式发行版；未发布清单时检查会失败。应用启动时自动检查，运行期间距上次成功检查满 24 小时后再次检查；用户可在设置中关闭。标题栏品牌右侧在发现更新后显示徽标，悬停或键盘聚焦可查看说明，点击后下载并安装。此前保存的设置若没有 `automatic` 字段，会采用新的默认开启行为；以后关闭时会明确保存 `false`。

首次上线需要一个过渡版本：未内置此 GitCode 地址和公钥、且没有配置兼容更新源的旧版本，不能自动发现新源，用户须先手动安装过渡版本。之后再发布版本号更高的正式版和对应签名清单，过渡版本才能显示更新徽标；与当前版本相同的清单不会触发更新。

已有的自定义清单地址和公钥继续优先使用；未配置自定义来源时才使用内置 GitCode 来源。长更新说明可在标题栏弹层中滚动查看，也可在更新设置中查看。

### GitCode 发布配置

GitCode 发行版 API 返回的是元数据，而不是签名信封。客户端支持 `gitcode` 源类型：先读取公开仓库的最新正式发行版标签，再从该发行版下载 `releases.json`，依旧必须通过内置公钥验签，安装包地址也只能来自签名清单。GitCode 仓库须支持不登录的 HTTPS API 和附件下载；实际服务的重定向、缓存及匿名访问需由发布者手动确认。

默认已配置为你的 GitCode 仓库，Windows 发布环境可直接构建过渡版本：

```powershell
./scripts/build-windows-installer.ps1 -Architecture amd64
```

该构建继续使用内置的发布公钥；私钥无需上传 GitCode。为更高版本生成清单时，使用 `./scripts/prepare-gitcode-update.ps1 -Installer <安装包路径> -NotesFile <日志路径> -Tag <实际发行标签>`，将生成的 `releases.json` 和安装包上传到同一个公开 GitCode 正式发行版。现有应用内置的是 GitHub 地址，因此须先手动安装使用 GitCode 地址构建的过渡版本。GitCode 上的操作和兼容性尚未实测，实际地址以仓库及官方接口为准。

从设置页选择“安装更新”会显示下载进度；从标题栏徽标操作会打开下载进度弹窗。下载并完成校验后，用户可选择“重启安装”；应用不会在下载完成后自动退出。下载可取消；暂存结果在应用退出或用户选择“放弃下载”时清理，自动检查不会删除已下载的更新。暂存期间手动检查会提示先安装或放弃下载。安装器在启动前重新检查签名清单和文件摘要；独立程序包仍由更新辅助进程重新校验。

更新检查和安装包下载使用应用中配置的代理路由，包括系统、手动和环境代理；不会携带下载任务的 Cookie 或站点认证信息。如果无法连接 GitCode，可先在设置中配置可用代理，或在发布新版时将清单和安装包迁至可访问的 HTTPS 源。

发布者的私钥位于 `C:/Users/kindr/.config/opendl-release-keys/private.key`，仅供发布者使用；请离线备份并保护，不要提交或上传私钥。生成新安装包并对其完成必要的代码签名后，准备 UTF-8 更新说明文件，手动执行：

```powershell
./scripts/prepare-gitcode-update.ps1 -Installer 'build/windows-amd64/OpenDL.Setup.版本号.amd64.exe' -NotesFile 'release-notes.txt'
```

脚本签名前比较私钥携带的公钥与源码内置的公钥，避免误用其他发布密钥；若正式版构建通过链接参数覆盖了公钥，发布时须传入与用户已安装版本一致的 `-ExpectedPublicKey`。更换密钥需要先通过旧密钥发布信任新公钥的客户端，不能仅替换服务器上的清单。

脚本根据 `mygo.json` 的稳定版本和最终安装包生成并签署 `releases.json`，要求文件名与构建脚本生成的版本及架构名称一致。默认发行标签为 `v<版本号>`；如果 GitCode 发行版标签不带 `v`，必须传入 `-Tag <版本号>`，否则清单中的安装包地址会返回 404。若原输出目录已有清单，可用 `-OutputDirectory <已有目录>` 生成新清单而不覆盖旧文件。将安装包和 `releases.json` 一起上传至对应的 GitCode 正式发行版；发布者手动确认最新发行版链接及完整更新链路。清单默认 90 天过期，须在过期前重新签署并替换附件。若同时发布两个 Windows 架构，可用 `-Architecture amd64 -OtherInstaller <arm64安装包路径>` 一次生成包含两个包的清单；`-Architecture` 对应主 `-Installer`，另一个参数对应另一架构。文件名检查不能证明包内程序的架构，发布者仍须确认实际内容。其他平台按下方完整清单协议生成；原 GitHub 发布脚本仍可使用。

## 发布协议

发布端提供 JSON 信封：`{"payload":"Base64 原始清单字节","signature":"Base64 Ed25519 签名"}`。签名覆盖完整原始字节，客户端先验证签名，再解析字段。

协议 v1 的清单仅接受稳定版，带预发布标识的候选版本会被拒绝；已安装的预发布版本仍可按 SemVer 升级到更新的稳定版。数字部分以字符串长度和字典序比较，不受 64 位整数上限影响。检查失败或取消后，界面会清除上次的可安装结果，需要重新成功检查才能安装。

清单字段：

| 字段 | 含义 |
| --- | --- |
| `schema` | 固定为 `1` |
| `version` | 稳定版 `major.minor.patch`，可带 `v` 前缀 |
| `expires` | RFC3339 过期时间；过期清单不能安装 |
| `notes` | 版本说明，按普通文本显示 |
| `assets` | 平台包数组；同一 `os` + `arch` + `kind` 只能有一项 |
| `assets[].os` / `arch` | Go 平台标识，例如 `windows` / `amd64` |
| `assets[].url` | 不包含登录凭据的 HTTPS 二进制地址 |
| `assets[].size` | 精确字节数，大于 0、最大 512 MiB |
| `assets[].sha256` | 安装包的 SHA-256 十六进制摘要 |
| `assets[].kind` | 可选；省略或 `binary` 为独立可执行文件，`installer` 为安装器升级包 |

协议 v1 的安装包可以是与当前平台匹配的**独立可执行文件**（默认）或**安装器升级包**（`kind: installer`，例如 EXE/MSI/PKG）。同一平台每种类型最多一项；客户端优先选择独立可执行文件，只有安装器时按安装器升级处理。ZIP、DMG 与应用包不在协议范围内。

安装器升级流程：下载后按签名清单校验大小与摘要，经系统提权（Windows 使用“以管理员身份运行”，用户取消提权时应用保持运行）启动安装器，应用随即退出。替换、备份与回退由安装器自身完成，更新器不参与也不做启动确认回退；安装器退出码与日志属于安装器行为。

仓库提供 `cmd/release-sign`。以下命令供发布者手动运行，本次没有执行：

```powershell
go run ./cmd/release-sign -generate D:/opendl-release-keys
go run ./cmd/release-sign -key D:/opendl-release-keys/private.key -manifest manifest.json -out releases.json
go run ./cmd/release-sign -verify releases.json -public D:/opendl-release-keys/public.key
```

`manifest.json` 由发布者填写，文件大小与摘要须来自实际二进制。工具保留输入原始字节生成签名，输出文件采用排他创建，避免覆盖既有密钥或清单。私钥只留在发布端；公钥在编译发布版本时内置。清单不能自动替换客户端公钥。

签名前工具检查稳定版本、过期时间、说明长度和所有平台包的 HTTPS 地址、大小、摘要及平台重复项。`-verify` 模式不签名：用公钥验证已生成的信封并检查全部平台包，不要求发布机的平台出现在清单中；可重复传入 `-asset windows/amd64=D:/release/OpenDL.exe` 复核指定的本地包。签名时一旦使用 `-asset`，必须覆盖清单中的所有包；验证时可以只复核指定的包。若同一平台同时提供两种包，使用 `-asset windows/amd64/binary=...` 和 `-asset windows/amd64/installer=...` 分别指定。工具比较实际文件大小与 SHA-256；未传入时仍需由发布者自行核对。签名后仍应保证上传的是同一文件。

## 发布源上线步骤

如改用 NAS 或其他静态托管，可按下列步骤自建；更换信任根或官方地址需要发布包含新配置的客户端：

1. 生成密钥（`-generate`）；私钥只留在发布机，公钥用于编译发布版本。
2. 填写 `manifest.json`（版本、过期时间、说明、各平台包的 HTTPS 地址与大小/摘要；安装器包标 `"kind": "installer"`），`-asset os/arch=路径` 让工具核对本地文件后签名。
3. 上传安装包与 `releases.json` 到任意 HTTPS 静态空间（对象存储、静态托管均可）；地址必须与清单声明一致且不含登录凭据。
4. `-verify releases.json -public public.key` 在本地演练一次（可带 `-asset` 复核上传前的文件），再用 curl 取回线上 `releases.json` 复验一次，确认传输无损。
5. 发布构建时向 Go 链接器传入 `-X main.officialUpdateURL=<HTTPS清单地址>` 和 `-X main.officialUpdatePublicKey=<Base64公钥>`，两项必须同时配置。确保打包流程将这些 `-ldflags` 传给最终的应用二进制；更新辅助进程使用同一内置公钥重新验证。配置后用户可直接检查更新或开启自动检查。发布前由发布者手动验证全链路。

注意事项：清单过期时间建议不超过 90 天（过期前重新签名发布）；静态服务器返回什么客户端就校验什么，压缩传输会被更新客户端拒绝；不要在 CDN 上改写 `releases.json`（缓存可保留安装包，清单建议短缓存）。

## 安装与失败恢复

1. 所有下载及重定向都要求 HTTPS；清单通过 Ed25519 校验后，校验版本、有效期、平台、大小及 SHA-256。
2. 文件暂存在当前可执行文件旁的独立目录，完整写入并同步后再次核对摘要。失败或取消不修改当前程序。
3. 用户选择“安装并重启”后才启动更新辅助进程；开发模式禁止安装，下载、任务校验、编辑及同步探测须先结束。下载更新前与暂存完成后都会检查；辅助程序是当前已安装程序的副本，Windows 下隐藏启动，不提前执行下载内容。

启动辅助程序前，下载引擎在调度锁下再次确认空闲并冻结新的任务工作；外部提交得到明确错误，直接添加的任务暂时保存为等待状态。辅助程序启动失败时解除冻结并恢复这些任务的调度。

辅助进程一旦成功创建，就按交接成功处理；释放进程句柄失败不会解除冻结或删除其安装计划。Windows 上辅助程序自身运行时可能无法删除自身副本，因此成功更新后暂存目录可能残留；包含旧版本或失败候选的目录会保留供恢复，不自动递归清理。
4. 旧进程退出并完成配置写入后，辅助程序重新读取公钥，重验签名及候选文件，确认安装目标仍是最初的文件，再保留旧版本并替换。
5. 新进程创建原生窗口后写入启动确认。45 秒内未确认或进程退出，则恢复并重开旧版本。恢复失败时保留暂存目录及旧版本，不递归删除文件。

安装器升级不使用上述辅助进程与启动确认：暂存目录在系统临时目录，成功启动安装器后保留供安装器读取，失败或取消时删除。

启动确认只说明程序已创建窗口，并不代替功能测试或配置迁移验证。已有下载记录、配置路径、接口标识及扩展通信协议不因更新而迁移。

验证或安装失败后若原版本成功重新启动，应用会按失败阶段显示提示；新版本启动失败并成功回退后也会提示。跨进程参数只包含固定阶段代码，详细错误输出到辅助进程日志，是否保存取决于运行环境。如果原程序无法重新启动，则无法在应用内显示提示，暂存目录会保留供排查。

尚待用户手动确认：签名错误、清单过期、大小/摘要错误、取消下载、目标被占用、无写入权限、启动失败回退、Windows/Linux/macOS 的实际进程行为。未运行构建或测试。
